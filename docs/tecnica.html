Cómo está construido Faro

Todo lo necesario para desarrollar, operar y extender la plataforma: arquitectura, modelo de datos, ciclo de vida de una corrida, seguridad, despliegue y las decisiones que explican por qué es así.

1. Arquitectura: tres planos

Faro separa estrictamente dónde vive cada cosa. Lo que pasa va a Postgres; cómo se trabaja va a git; quién ejecuta es un proceso sin estado. Esa separación es la que hace el sistema vendible: un comprador se lleva el método (git) y lo despliega sobre su propia infraestructura.

Platform

Next.js 15 (App Router, TS, Tailwind v4) sobre Supabase: Postgres con RLS en cada tabla, Auth para sesiones, Realtime para el feed en vivo y Vault para secretos. El portal nunca escribe estado de ejecución: escribe intención (crear un run, decidir un gate) mediante funciones RPC SECURITY DEFINER que validan el rol del que llama.

Engine

Un proceso Python de stdlib puro (engine/worker.py) que habla con Postgres únicamente vía PostgREST — cero drivers de base de datos. El loop: materializa corridas pedidas por la UI (expand_runs), crea las recurrentes por período (ensure_recurring_runs), reclama una fase (claim_phase, con FOR UPDATE SKIP LOCKED: Postgres es la cola), ejecuta claude -p con streaming de eventos, y cierra con finish_phase. Un reaper devuelve a la cola las fases huérfanas de workers muertos. Paralelismo = número de procesos worker; se reparten fases sin colisión por el propio lock de Postgres.

Method

Workflows (fases, dependencias, gates con clase), agentes (persona + skills), el catálogo de skills vendorizado y pineado (marketingskills v2.10.0, MIT) y AGENCY.md — las reglas que se inyectan en todas las fases. Cada bootstrap estampa el SHA de git en method_versions: toda corrida sabe con qué versión del método se hizo. El método nunca entra a la base de datos.

Conceptos que cruzan todos los workflows:

  • Gates con clase (money · craft · publish · measurement): cada pausa declara qué tipo de decisión es. La matriz rol × clase decide quién puede firmarla (un cliente solo aprueba publish de su cuenta).
  • builds_on: un workflow declara sobre qué trabajos previos construye; el engine inyecta el último entregable de esos jobs en el prompt. La semana N del loop siempre conoce la N−1.
  • Intake: el brief que el humano escribe al arrancar viaja a todas las fases como "What the human asked for", con la instrucción de no sustituirlo.
  • Engagement (audit · performance · full_funnel): qué compra la cuenta; limita qué workflows se pueden arrancar.

Las reglas de la casa (AGENCY.md) se inyectan en cada fase. Las que definen el producto: 1) ningún número sin origen (todo dato cita su comando o archivo fuente); 1b) los KPIs medidos viajan además como datos (bloque ```metrics con vocabulario canónico → tabla metrics → charts); 1c) comparaciones y tendencias llevan gráfica (bloque ```chart, solo con números ya presentes en el documento); 3) citar el skill en artefactos internos, nunca filenames internos en el entregable final; 5) nada se publica sin gate humano; 6) si una fase no puede hacerse, se declara — un hueco de datos jamás se rellena con estimaciones.

  • phases.status: blocked → pending → running → awaiting_gate → done | failed | rejected. Cada fase guarda además claimed_by, timestamps, cost_usd y tokens.
  • artifacts.content guarda el markdown completo del entregable — no hay archivos sueltos que respaldar aparte de Postgres.
  • metrics: una fila por KPI medido con source_path al documento que lo contiene. Borrar un run borra sus métricas en cascada — un número sin su documento de origen no puede existir.
  • gate_decisions: la decisión, quién la firmó (decided_name) y el feedback textual, que se inyecta en el redo si fue rechazo.

desbloquea la siguiente fase o re-encola el redo

Detalles operativos: cada fase corre en un directorio temporal que se destruye al terminar; el worker exporta las credenciales del cliente (descifradas de Vault) como variables de entorno y agrega los CLIs del vendor al PATH; los eventos llegan al portal por Realtime sin polling. Si un worker muere a mitad de fase, el reaper la detecta (pid muerto en el mismo host, o 15 min sin eventos) y la devuelve a pending — las fases son idempotentes.

5. Seguridad y roles

rolvedecide gatesadministra
ownertodotodas las clasessettings, conectores, borrado, miembros
account_directortodomoney · craft · publish · measurementsettings de cuentas
specialist / analysttodocraft · measurement—
client_viewersolo su(s) cuenta(s)solo publish de su cuenta—
  • RLS en todas las tablas, con helpers SECURITY DEFINER (is_staff, can_see_client, can_decide_gate = matriz rol × clase). La única escritura autenticada directa es la decisión de gate.
  • Vault: un secreto JSON por (cliente, tool). Solo engine_credentials() lo descifra, y solo service_role puede ejecutarla — un usuario del portal no puede leer secretos ni con SQL.
  • Vista de cliente: los costos AI, el log de agentes y los slugs técnicos existen solo para staff. El cliente ve pipeline firmado, documentos con nombre humano y resultados.
  • audit_log: cada request_run, decisión, conexión/desconexión de credencial y borrado queda firmado con nombre. Los borrados (owner-only) cascadean y se confirman tipeando el nombre de la cuenta.

6. Conectores

El catálogo (~52) se parsea del registry del vendor al manifest del método: id, variables de entorno requeridas y guía de setup. El owner conecta desde la web: el secreto va a Vault (set_connector), el flag del cliente pasa a true y queda auditado sin el valor. En cada fase, el worker inyecta las credenciales como env vars y el agente usa el CLI correspondiente (ga4, meta-ads, google-ads…), pegando comando y respuesta real como evidencia. Tool no conectado = hueco declarado, nunca un número inventado. La fase execution del loop ejecuta cambios reales solo tras el gate de dinero, y solo lo aprobado.

7. Costos y métricas

El evento result de cada sesión claude deja en la fase cost_usd, tokens_in (incluida caché) y tokens_out. El desk agrega el mes en curso por cuenta y por organización; cada gate muestra lo que costó producir aquello que se está aprobando. Las métricas de negocio (spend, CAC, conversiones…) se extraen de los bloques ```metrics de los entregables con su documento de origen, se deduplican por período en lectura y alimentan los tiles con sparklines de cada cuenta.

8. Internacionalización

Resolución: cookie del selector (topbar y login) → Accept-Language del navegador → idioma del cliente (para viewers) → inglés. Diccionario en lib/i18n.ts; nombres de workflows/fases/documentos como vocabulario traducido en lib/names.ts. El contenido de los entregables sigue el language de cada cuenta y el export a PDF usa el idioma del cliente (el documento le pertenece). Agregar un idioma = rellenar dos diccionarios.

  • Esquema como código: 13 migraciones SQL en supabase/migrations/; bootstrap.py crea usuarios/org, publica el manifest del método y es idempotente — nunca toca clientes que ya viven en la base ni resucita corridas borradas.

10. Desarrollo local

# stack de datos
supabase start                      # Postgres/Auth/Realtime/Vault en :54321-54324
psql -f supabase/migrations/*.sql   # o supabase db push
python3 engine/bootstrap.py         # org, usuarios, manifest del método

# portal
cd webapp && npm i && npx next build && npx next start -p 3000
# login dev de un clic (solo contra Supabase local): owner / client

# engine
python3 engine/worker.py            # loop; --once para una fase; enqueue <slug> <workflow>

Convenciones: cambios de método con [ADR] en el commit; verificación visual con screenshot antes de declarar hecho un cambio de UI; los tests de escenarios usan el LLM guionado del repo para no gastar sesiones reales.

11. Decisiones que explican el diseño

decisiónpor qué
Postgres es la cola (SKIP LOCKED)cero infraestructura extra; N workers escalan sin coordinador
El método vive en git, no en la DBes la IP vendible; versionable, auditable, portable
Engine solo por PostgREST/RPCsin drivers ni pool; la superficie de escritura son 6 funciones auditables
La ejecución post-gate es una fase del métodoel engine se mantiene tonto; una fase ya sabe correr CLIs y citar evidencia
Métricas extraídas de los entregables"todo número con origen" verificable por máquina; sin segunda vía de escritura
Export = vista imprimible, no generador PDFcero dependencias; mismo RLS; el navegador hace el PDF
Costos por fase desde el evento resultmargen real por cuenta sin instrumentación extra
